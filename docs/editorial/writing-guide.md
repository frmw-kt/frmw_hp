**版: v6（2026-10-10）** — 変更履歴と理由は [改善記録](improvement-log.md)。企画メモには準拠した版を書く。

## 目的・担当

主指標は記事（`/blog/<slug>`）への自然検索クリック数。表示回数・CTR・検索語別順位を補助指標、PVを参考指標とする。事業の最終目的は無料相談（`/contact`）につながることだが、frmwの顧客にならない検索流入や、中身と合わないタイトルを増やさない。実測データがなければ効果・検索ボリューム・順位を推測で数値化しない。

- 読者: 年商数千万〜数億円規模の事業者の経営者・マーケティング担当（広告運用・Web集客・SNS・LP改善に手が回らない／外注を検討している）。
- `seo` はテーマ選定・競合調査・既存記事との重複確認（読み取り専用）、`seo-writer` は個別記事の調査・執筆・検証を担当する。サイト全体の実装は `engineer`、文面の訴求・ターゲティングは `marketing_lead` の領域。連携先が使えなくても個別記事の調査は自分で行い、未実施の項目を明記する。

## 執筆前の判断（企画メモ）

`seo` の調査があれば確認日と根拠を見て再利用し、不足だけ補う。直接の依頼でも、次の企画メモを作ってから執筆する。構成ごとの確認待ちは通常不要。

メモは `hp/docs/editorial/articles/<slug>.md` に保存する。未確定テーマは候補スラッグで保存し、採用時に既存ファイルとの重複を確認する。顧客の個人情報・取引先名（公開許可のないもの）を残さない。

```markdown

- 準拠したガイドの版：v6

- 主検索語／関連する検索語：
- 表記ゆれ・言い換え（読者が実際に使う呼び方。下の表に書く。**表の語はすべて、反映先か入れない理由を書く**。検証で照合される）：

| 呼び方 | 種類（公式/一般/旧称/略称） | 反映先（title/description/h2/本文） | 入れない理由 |
|---|---|---|---|

- 主検索語の問いへの直接の答え（冒頭で答える一文）：
- summary（結論。2〜3文）／takeaways（この記事でわかること。3〜5点）の下書き：
- FAQの候補（本文で答え切れない具体的な疑問と、その出どころ＝検索上位記事・検索結果の関連する質問・公式ヘルプのよくある質問のどれか。3問未満なら置かない）：
- 独自性の型（判断基準／チェックリスト／診断の順序／条件を明示した試算 のどれを、どのh2に置くか）：
- 読者・状況・解決したい疑問：
- 記事が伝える結論：
- descriptionの下書き（答えの要点＋読者の状況。例: 「〜を検討中の事業者向けに」「〜の場合は」）：
- 新規／リライト、その理由・対象URL：
- 各h2の1文目（その節の問いへの答え。並べて読んで記事の要約になっているか確かめる）：

- 確認した既存記事と、それぞれが答える疑問・役割の違い：
- 検索結果の確認日・検索語・取得環境・参照URL：
- 参照ページから分かった論点／自社が追加できる価値：
- 構成・内部リンク先（サービスページ・関連記事）と必要な理由：
- 被リンク元（この記事へリンクを足す既存記事と、その箇所）：
- 図解の候補（図にしたほうが分かりやすい箇所を**すべて**挙げる。下の表。検証で記事の図の数と照合される）：

| 図解の候補（箇所） | 図の種類（流れ・比較・構造・時系列・計算・分岐・位置関係） | 判断（作成／作らない） | 作らない理由（作成なら空欄） |

- 子記事ができたら本文にリンクを足す位置（柱記事の場合。未作成の記事は本文で予告しない）：
- 業種別の当てはめ例（問い合わせ型、予約・来店型、EC型など、必要なもの）：
- 次回見直し予定日（媒体仕様・料金・法令を扱う記事は3〜6か月後）：
## 主張と根拠
| 主張・掲載箇所 | 一次資料URL・資料名 | 確認日・適用条件 | 判定 |
```

- タイトル・カテゴリだけでなく、既存本文が答える疑問を比較する。同じ意図なら既存記事の強化（リライト）を基本にし、新規記事を乱立させない。URL変更や記事削除を独断で行わない。
- 検索結果の上位ページを実際に開き（目安3〜5件、最低1〜2件）、見出し構成・扱う論点・具体例の粒度を確認する。検索ツールで見えない広告・関連質問・順位を観測済みとしない。上位ページの特徴（文字数・表の数など）をランキング要因と断定しない。
- 自社が追加できる価値を決める。例: 年商数千万〜数億円規模の事業者に合わせた予算配分の考え方、実務の手順・チェックリスト、判断の分岐、条件を明示した試算。競合の言い換えや文字数の上乗せだけにしない。
- 検索できないときは企画・構成案まで進めて未検証と記録する。未確認の主張を含む原稿を公開可能な完成原稿としない。
- **時間が限られるときの優先順位**: ①本文の主張を支える一次資料の確認 → ②検索上位記事の本文確認（最低1〜2件。読めた件数を企画メモに書く）→ ③図解・補足。②を減らしても①は減らさない。確認しきれない論点は本文から外して未解決事項に書く。

## 根拠と文章

- 広告媒体の仕様・審査基準・料金体系・機能の有無（Meta広告、Google広告、Yahoo!広告、LINE広告、各SNS）は、各社の公式ヘルプ・公式ブログ・公式ドキュメントを実際に開いて確認し、確認日を記録する。仕様は頻繁に変わるため、記憶や他社ブログの記述で代用しない。
- 検索の仕組み・SEOは Google 検索セントラルなどの公式資料、法令（景品表示法・ステルスマーケティング規制・特定商取引法・特定電子メール法・個人情報保護法など）は消費者庁・総務省・個人情報保護委員会・e-Gov法令検索などの一次資料で確認する。法令は「一般論の解説」にとどめ、個別の法的判断をしない。税務（消費税・インボイス・リバースチャージ等）は国税庁の一次資料で確認できた一般的な仕組みだけを書き、個別の会計・税務処理は「経理担当者・税理士に確認」と書く（確認できない取扱いは書かない）。
- 統計・市場規模は公的統計や調査の発行元の資料を確認する。調査会社のプレスリリースを引く場合は調査方法・対象・時期も併記する。
- 裏付けのない重要な主張を「一般的に」「といわれています」で通さない。根拠がなければ削除・保留する。主題の結論を支える根拠が足りなければ原稿を未完了として扱う。
- **自社実績・事例・数値・お客様の声を創作しない。** 使えるのは `hp/src/lib/cases.ts` の公開事例と `site.ts` 等に既に掲載している事実のみ。未公開・仮の事例（例: 事例ページの仮文面）や、根拠を確認できない実績表現は使わない。迷う場合は社長に確認し、確認できるまで本文に入れない。
- 「必ず成果が出る」「最安」「No.1」など、根拠のない断定・最上級表現（景品表示法上の問題になりうる表現）を使わない。他社を名指しで批判しない。
- 試算は前提（予算・単価・CVR・期間・含めない費用・丸め）を明示し、計算で再現できるようにする。仮定の試算を実在事例や保証値として見せない。
- 冒頭で読者の疑問に答え、条件や例外を近くに置く。不安を煽らない。専門用語（CPA・ROAS・CVRなど）は初出で説明する。
- 図や本文を足したら `readTime` を直す（本文の文字数÷500の切り上げ。figcaption の文字も本文に数える。検証で±1分を超えると警告）。
- 文字数、表、FAQ、リンク数は合格条件ではない。比較には表、手順には番号付きリスト、補足にはH3など、情報に合う表現を選ぶ。
- タイトルと description は記事の答え・対象・読む価値を正確に表す。年号は時点が重要で内容も確認した場合だけ使う。description には、一次資料で確認した数値・条件があれば入れる（例: 「週50件」「月10万円なら1件約465円以下」）。「完全ガイド」「徹底解説」「決定版」など中身を示さない煽る語は使わない（検証で警告）。
- **リライト時のタイトル変更**: 未公開の記事は、主検索語の問いに合わせて変えてよい。公開済みの記事は、検索結果での表示（Search Console の表示回数・CTR）を確認できる場合に理由を企画メモに書いて変える。どちらも slug・URL・公開日（`date`）は変えない。
- **柱記事と子記事**: 柱記事は全体像・手順の流れ・判断の分岐が役割で、詳細は子記事に任せる。1つのh2が長くなる（目安1,500字超。検証で警告）場合は、①手段・手順ごとの説明なら h3 を h2 に格上げして分ける、②1つの論点を深掘りしているなら子記事の候補として企画メモに残し、柱では要約にとどめる。まだない子記事を本文で「別の記事で扱う予定」と予告しない（古い約束になるため）。差し込み位置は企画メモの「子記事ができたら本文にリンクを足す位置」に書き、子記事を書いた担当が被リンクの提案に使う。
- **ヘルプのページ名と本文の用語が違う場合**（例: ページ名「オーディエンス管理」・本文「オーディエンス制御」）: 出典へのリンク文字はページ名、本文の説明は本文の用語で書く。
- **画面の名称（UI名）**: 日本語の公式ヘルプで確認できた名称だけを［］（全角）付きで書く（半角の [ ] は使わない。「」は引用と強調）。［］はボタン・メニュー・タブ・入力欄など公式ヘルプが [ ] で囲む操作対象に使い、選択肢・ステータスの名前は「」で書く（glossary 参照）。日本語版がなく英語版しか確認できない場合は、［］付きの名称を書かずに操作の内容で説明する（必要なら英語の表記を併記して「英語版ヘルプの表記」と明記）。UI名は変わりやすいので確認日を企画メモに残す。
- **時点の但し書き**: 媒体の仕様・料金・法令・制度を扱う記事は、本文の冒頭近く（遅くとも最初のh2の中。検証で位置を確認）に「◯年◯月◯日時点の公式情報に基づきます」と書く（発行元を足すなら「2026年10月10日時点の公式情報（Google 広告ヘルプ）に基づきます」。検証は「時点の」から「に基づ」まで30字以内を拾う）。本文の途中で時点を繰り返すのは、変わりやすい数値・期間（審査にかかる時間、料金、手数料率、期限など）を書く文だけでよい。日付は**媒体仕様・料金・法令の出典をまとめて開き直して確認した日**で、その出典の `accessedAt` と同じになる（検証で、どれかの出典の確認日と一致するかを照合）。統計など一部の出典だけを開き直した場合は、その出典の `accessedAt` だけを更新し、但し書きの日付は変えない。`accessedAt` は実際に開いて確認したときだけ更新する（本文を直しただけでは更新しない。品質チェック11の「確認日も更新」も、開き直した出典に限る）。仕様の説明として過去の日付に触れる文（「◯年◯月◯日時点では〜でした」）はこの但し書きとは別。
- **時期が重要な記事（サービス終了・名称変更・制度の改定など）**: 公式で確定した日付はそのまま、予定の日付には「（予定）」「〜頃（予定）」を付けて書き分ける。本文の早い位置に「〇年〇月〇日時点の公式発表に基づく」と書く。タイトルには原則として日付を入れない（過ぎると古くなる）。次回見直し予定日は、最も近い重要な日付の直後に置く。重要な日付が複数あるときは、企画メモに「次回見直し予定日：2026-10-14（ビジネスIDの自動統合の後）、2026-11-06（配信停止の後）」のように近い順に並べる（検証は最初の日付を読む）。summary・faq の中の「◯年◯月◯日時点」も、見直しのときに本文の但し書きと一緒に更新する（検証で出典の確認日と照合）。
- **PDFの一次資料**: この環境では PDF の本文を読めない（WebFetch はバイナリ保存のみ、テキスト抽出ツールなし）。PDF にしか書かれていない内容は未確認として扱い、本文に入れない（HTML の告知ページ・ヘルプで確認できる範囲で書く）。
- **業態の呼び方**: 「問い合わせ型」「予約・来店型」「EC型」。記事の主題に公式の区分がある場合（例: Googleビジネスプロフィールの「実店舗」「非店舗型」「ハイブリッド型」）は、本文の判断は公式の区分で書き、業態別の当てはめの節で3つの業態に対応づける。並べるときは読点で区切る（「問い合わせ型、予約・来店型、EC型」。「・」で並べると「予約・来店型」と区別できない）。
- **英字と日本語の間の空白**: 本文では入れない（例: 「LINEのトークリスト」「Googleマップ」）。ただし公式の正式名称に含まれる空白はそのまま（例: 「LINEヤフー広告 検索広告」。出典名・画面名は公式表記のまま）。
- **公式資料が外貨・海外の例しか示していない場合**: 本文で使うなら「公式の例（米ドル）」と明記して原文の通貨のまま示し、円に換算した額を公式の値のように書かない。日本で適用される額が確認できないときは「決まり方と確認する場所」で答える。
- 内部リンクは次の疑問を解く場所に置き、具体的なアンカー名を使う（例:「[広告運用代行の支援内容](/services/operations)」）。**まとめ以外の本文に、関連記事またはサービスページへのリンクを1本以上置く**（まとめの段落にだけ並べない）。記事末尾の共通CTA（相談への案内）は表示側で自動表示されるため、本文に同じ営業段落を重ねない。まとめで自然に触れる程度にする。
- 外部リンク・出典は HTTPS。本文中の出典参照は `[資料名](#source-<id>)` とし、記事の `sources` に資料を登録する。同じ資料を2回目以降に引くときは短い名前（例: 「Meta：広告のレベル」）でよい（長い資料名で段落が読みにくくならないように）。

## 全記事共通の品質チェック

2026-10-06 の1本目（`meta-ads-small-budget`）のレビューとバッチ1の完了報告で見つかった、どの記事にも当てはまる観点。企画メモの項目と対応させ、執筆後にも見直す。

1. **検索語の問いに冒頭で直接答える**: 「〜はいくらから」「〜とは」など主検索語そのものの問いに、冒頭の数段落以内で答える。正確な値を一次資料で確認できない場合も黙って外さず、「何によって変わるか」「どこで確認できるか」を答えとして示す。
2. **表記ゆれ・言い換えを拾う**: 読者が使う呼び方（例: Meta広告／Facebook広告／インスタ広告、学習期間／情報収集期間、LP／ランディングページ）を企画メモに書き出し、主要なものをタイトル・description・見出しのいずれかと本文に自然に入れる。同じ語の詰め込みはしない。媒体の公式用語と一般的な呼び方が違う場合は、初出で両方を示す。
3. **frmwの読者に当てはめる**: 読者は業態がさまざまなので、手順・判断が業態で変わる場合は、問い合わせ型（工務店・士業など）、予約・来店型（店舗・クリニックなど）、EC型などの当てはめ例を示す。数値の例は仮定と明記し、実在の事例のように見せない。
4. **図にしたほうが分かりやすい箇所は、すべて図解する（枚数の上限なし）**: 手順・流れ、比較、仕組み・構造、時系列（日程・期限）、計算の過程、判断の分岐、画面や配置の位置関係など、文章や表より図のほうが早く正確に伝わる箇所は、記事内に何か所あってもそれぞれ SVG の図解にする（作り方は [記事形式](article-format.md#図解画像)）。企画メモの「図解の候補」に該当箇所をすべて挙げ、作らない場合は理由（表のほうが正確・文章で十分・根拠のある数値がない等）を書く。図の中の文字・数値も本文と同じく根拠が必要。装飾目的の画像や、本文の言い換えにしかならない図は作らない。
5. **内部リンクは双方向にする**: 新しい記事から既存記事へのリンクに加えて、関連する既存記事の該当箇所から新しい記事へのリンクを1〜3本足す（新規記事がコラム一覧からしか辿れない状態にしない）。リンクは次の疑問を解く位置に置き、無関係な記事に足さない。`check:articles` は他の記事からリンクされていない記事を警告する。同じまとまり（topic-map のクラスタ）に既存記事が3本以上あれば、本文から3本以上にリンクできないか確かめる（リンク数は合格条件ではない。次の疑問を解く位置がなければ足さない）。
6. **FAQは読者の疑問のために置く**（検索上位記事によくある誤り・食い違いを公式の値で正す疑問も出どころに含めてよい（例: 「月の予算は1日の予算×30か」→ 公式は30.4）。回答の1文目は「あります。」「できます。」だけにせず、主語と結論を1文で書く: 「Meta広告の1日の予算は、その日に最大75%多く使われることがあります。」。出どころは検索上位記事・検索結果の関連する質問・公式ヘルプのよくある質問のどれかで、企画メモに書く）: Google の FAQ リッチリザルトは、よく知られた政府・医療系サイトに限って表示される（[Google 検索セントラル: よくある質問（FAQ）の構造化データ](https://developers.google.com/search/docs/appearance/structured-data/faqpage)）。検索結果の見た目を目的にFAQを追加しない。検索上位記事・関連する質問で見つけた、**本文で答え切れない具体的な疑問が3問以上**あるときだけ、記事データの `faq` に書く（表示側で記事末尾の「よくある質問」と FAQPage の構造化データになる。本文に「よくある質問」のh2は作らない）。回答は40〜300字で、質問だけを読んだ人にも通じるよう主語から書き、本文の文をそのまま繰り返さない（検証で警告）。数値には条件を付ける。回答にはリンクを入れられないので、根拠は資料名で書き（例: 「Metaのヘルプ『1日の予算について』によると」）、同じ資料を `sources` に登録して本文でも参照する。
7. **公式の日本語版が機械翻訳の場合は英語版と照合する**: Google ヘルプなどで「AI翻訳を含む場合がある」と注記された日本語版は必ず、注記のない日本語版（Meta など）も意味が曖昧な場合は、本文の根拠にする要点のうち**条件・禁止事項・推奨の程度（〜できる／〜すべき／〜が上がる 等）を表す文**を英語版と照合し、意味が強すぎる・弱すぎる場合は控えめな方（多くは原文）に合わせる。用語の定義や仕組みの説明だけの引用は照合しなくてよい。照合したことを企画メモに書く。
   - **定義からの帰結**: 公式の定義から論理的に導いた記述（例: 同じ行動を2つの成果として数えると二重に計上される）は、公式がそう書いているかのように書かず、根拠の定義へのリンクを付けて「〜という定義なので、〜になります」と導き方が分かる形にする。企画メモの判定は「定義からの帰結」とする。
   - **WebFetch の要約をそのまま根拠にしない**: WebFetch は要約モデルを通すため、原文にない内容が混ざることがある（実例: web.dev の要約に原文にない推奨が入っていた）。本文の根拠にする文は「原文のまま抜き出して」と指示して取得するか、`read-page.mjs` で原文を確認する。
   - **一次資料の対象と記事の対象がずれる場合**（例: 資料は「登録フォーム」向け・記事は「問い合わせフォーム」）: 本文で資料の適用対象を明記し、記事の対象へ当てはめる部分は「〜にも当てはまります」と分けて書く。
   - **公式同士で適用範囲が違うとき**（例: あるページは一般的な説明、別のページは「一部のアカウントで段階的に導入中」）: 両方に当てはまる控えめな書き方にし、食い違いを未解決事項に書く。
   - **公的統計がない数値（業種別の比率など）**: 民間の調査・集計を使う場合は、発行元・調査方法・対象・時期を本文に併記し、「目安」ではなく傾向や差を示す根拠として使う。出典のない業界平均は使わない。
   - **公式の定義がない業界用語**（例: 許容CPA・限界CPA・商談化率）: 本文の初出で「この記事では〜を〜とします」と定義を明示する（分母のある指標は分母も書く）。glossary の書き方に合わせる。
8. **公式と第三者の記述が違うときは公式を採用する**: 第三者の記事で見つけた数値・仕様の変更（例: 必要件数が下がった等）は、公式の一次資料で確認できるまで本文に入れず、食い違いを未解決事項に記録する。
9. **JavaScriptで描画される公式ページ**: Meta ビジネスヘルプセンターなどは WebFetch では本文を取れないことがある。取れない場合は「読めなかった」と扱い、推測で埋めない。`seo-writer` は補助スクリプトで本文を読める: `cd /Users/k/Projects/frmw/autosales && node scripts/read-page.mjs <https://URL> [--max=20000] [--links=キーワード]`（Playwright は autosales にのみ導入。hp には入っていない。一時ファイルを作らないので並行実行してよい）。`--links` で関連ページのURLも拾える。読み取り専用の `seo` は未確認として申し送る。
10. **既存記事の根拠も見直す**: リライト時は、既存の本文・title・description にある実績表現や数値（例: 「平均◯%改善」）も `cases.ts` の公開事例など根拠と照合し、確認できないものは表現を改めるか社長に確認する。
11. **鮮度を管理する**: 媒体の仕様・料金・法令を扱う記事は、企画メモに次回見直し予定日を書く。`check:articles` は確認日（`accessedAt`）から180日以上たった出典を警告する。見直しで内容が変わったら `updatedAt` を更新し、出典の確認日も更新する。
12. **節だけを抜き出されても意味が通るように書く**: 検索結果やAIによる回答は、記事の一部の段落だけを引用することがある。各h2の**1文目で、その節の問いに主語つきで答える**（「この」「上記」「以下」「そのため」で始めない。検証で警告）。見出しは答え（主張）か具体的な問いの形にする（例: 「最小予算は業種・入札戦略・最適化などで決まる」「月10万円で学習を進めるには、1件いくらで取れればよいか」。「〜について」「〜とは」「〜の関係」「〜の注意」「〜の進め方」など話題名だけの見出しは警告）。見出しは目次にも出るため50字以内（検証で警告）にし、答えの核だけを見出しに、条件は1文目に回す。1文目は「次のように説明しています」「以下のとおりです」「次の仕組みで換算します」のような前置きにしない（検証で警告）。見出しに式・数値の答えがある節は、1文目にもその式・数値を書く（答えを表の中だけに置かない）。**表・図の直前の文は、表・図から言える結論を書く**（「同じ月10万円でも、広告セットを5つに分けると1件あたりの上限は約93円まで下がります」。「下の表は〜の試算です」だけにしない。検証で警告）。図番号は出現順（検証で警告）。1文目で答えを言い、その段落の直後に表・図を置く場合は、表・図の前に別の結論の文を足さなくてよい（同じ結論を近くに2回書かない）。番号付きリストが結論を言い切っている場合は、リストの直後に図を置いてよい。h3 も話題名だけにせず、答えか問いの形を目指す（検証はh2のみ）。「まとめ」の見出しは対象外（「まとめ：〜」と答えを足してもよい）。数値は条件・時点と同じ文に書く（「週約50件（情報収集期間を抜ける目安。Meta公式）」）。
13. **冒頭の型（summary・takeaways）**: 記事データの `summary`（結論。40〜200字、2〜3文）と `takeaways`（この記事でわかること。3〜5点）を書く（表示側でタイトル下の囲みになり、`summary` は llms.txt の記事の説明にも使う）。役割分担: `description` は検索結果に出る説明文で、読者の状況と記事で得られる判断材料を書く（記事ページでは `summary` がある場合は表示しないので、summary との書き分けは求めない）。`summary` は主検索語の問いへの答えと最大の条件（summary だけ引用されても誤用されないよう、数値・式の単位や分母まで書く）、本文の冒頭段落はその根拠と前提（出典つき）、`takeaways` は各h2で得られる判断材料、**まとめは summary の繰り返しではなく、読者が次にやること（どの画面で何を確かめるか、何を計算するか）で締める**。summary と冒頭段落・まとめに20字以上の同じ文字列があると検証で警告（括弧書きは除く）。summary・takeaways にタグは使えず、出典リンクは本文に置く。
14. **独自性の型**: 自社の実務経験・運用実感を根拠にした記述は書かない（2026-10-10 社長判断。実績・事例の創作禁止とあわせて）。「当社の経験では」と明示した文だけでなく、**主語のない実務感覚の一般化**（「数日の数字を見て設定を変えたくなりがちです」「まとめて行うのが現実的です」「社内で説明しやすくなります」）も同じ扱い。出典・計算・定義のどれにもつながらない文は、削るか公式の記述に置き換える（例: 「Metaは情報収集期間中はパフォーマンスが安定しないとしています」）。検証は「〜がちです」「〜しやすくなります」などの言い回しを候補として一覧に出す（候補なので、根拠がつながっていれば残してよい）。そのかわり、各記事の主要部分に次のどれかを最低1つ置き、企画メモの「独自性の型」に書く: ①判断基準（どの条件ならどちらを選ぶか）②チェックリスト（番号付き。症状→確認箇所）③診断の順序（どの数字・どの画面から見るか）④条件を明示した試算。frmwが作った図には figcaption の末尾に「（Framework作成）」と書く（v6以降の記事は検証で確認）。公式資料をもとにした図は「…。Meta「情報収集期間について」をもとに作成（Framework作成）」のように、もとにした資料名を前に書く。公式の定義をもとに順番や判断に並べ直した図も同じ形で、作成者は末尾の（Framework作成）だけに書く（「…の定義をもとに、確かめる順に並べたもの（Framework作成）」）。公式ヘルプの内容を frmw が手順・チェックリストに並べ直した場合は、本文で「Meta公式ヘルプの内容を、Frameworkが確かめやすい順に並べたものです」のように**並べたのは自社、内容は公式**と分けて書く（自社の経験談にしない）。
15. **記事に合わせた相談の案内（cta）**: `cta.lead` に、その記事の読者が次に相談したくなる具体的な一文を書く（例: 「粗利から許容CPAを出すところから、一緒に計算します」）。表示側で本文の中盤と末尾に出る。frmw の支援内容（`services.ts`）にない作業を約束しない。煽らない。本文に別の営業段落は書かない。境界: 本文のサービスページへのリンク（評価基準9）は、支援範囲の説明として置く（「〜の支援内容は運用代行のページにまとめています」）。「ご相談ください」「お気軽に」などの誘いは本文に書かず cta に任せる。

### サイト側の課題（記事ごとには直せないもの。`engineer` の担当）
記事の作業中に気づいた場合は完了報告に書き、勝手に共通部品を直さない。
- **対応済み（2026-10-06）**: 記事ごとのOGP画像（`/blog/<slug>/og-image`。タイトル・カテゴリ入りで自動生成）を `og:image`・`twitter:image`・Article構造化データの `image` に使用／`twitter:title`・`twitter:description` を記事ごとの値に／`og:type=article`・公開日・更新日・カテゴリ／記事末尾に同じカテゴリの関連記事（最大3本）とカテゴリに応じた支援ページへのリンク／本文の図解（SVG等）に対応／サイトマップの更新日を実際の更新日だけに
- **対応済み（2026-10-10）**: `summary`・`takeaways`（タイトル下の囲み）、`faq`（記事末尾の「よくある質問」と FAQPage の構造化データ）、`cta`（本文の中盤と末尾の相談の案内）、Article の構造化データの `keywords`、`/llms.txt`（会社・サービス・全記事を記事データから自動生成）。パンくずの BreadcrumbList は以前から出力済み
- **未対応**: 記事の著者表示が「編集：Framework」のみ。人物の著者情報（実在の経歴）を出す場合は社長の確認が必要で、創作しない（Google は著者が人物なら `url` でプロフィールページを示すことを推奨: [Google 検索セントラル: Article の構造化データ](https://developers.google.com/search/docs/appearance/structured-data/article)）
- 記事末尾の自動の関連記事は「同じカテゴリの新しい順に3本」なので、同じまとまり（クラスタ）の記事同士のリンクは本文で張る

## 並行執筆のルール（統括から複数の記事を同時に依頼された場合）

- 自分の記事のファイル（`hp/content/blog/<slug>.json`・`hp/docs/editorial/articles/<slug>.md`・`hp/public/images/blog/<slug>/`）だけを作成・編集する。一時ファイルを作らず、削除コマンドも使わない。開発サーバー（:3000）は起動・停止しない。新しい記事も再起動なしで `/blog/<slug>` に表示される（2026-10-06 修正）。**他の記事・共通部品・基準文書は編集しない**（同時編集で壊さないため）。
- 他の記事から新しい記事へのリンクは、完了報告で「被リンクの提案」（対象記事のslug・挿入する位置の直前の文・アンカー文言・挿入する文）として出す。反映は統括が行う。
- 同じバッチの記事が作業中に完成した場合は、自分の本文からリンクしてよい（`check:articles` が存在を確認する。公開時に相手が未公開ならリンク切れになるので、統括が公開の組み合わせを確認する）。
- 書き終えたら、同じバッチの他の記事のうち自分と論点が重なるもの（依頼文に書かれた同時執筆の記事）を読めるなら読み、用語の書き方・主張が食い違っていないか確かめる。食い違いや、他の記事で確認済みの事実（自分の未解決事項が解けるもの）があれば完了報告に書く（相手の記事は編集しない）。
- **利用量を抑える読み方**: topic-map は担当テーマの行と「線引き」だけを grep で読む。公式ページは `read-page.mjs --max=5000` から始め、必要な部分だけ追加で読む。同じページを何度も取得しない（取得した要点は企画メモの「主張と根拠」に書いておく）。
- （統括向け）同時に動かす執筆担当は2〜3体までにする（2026-10-06、4体の同時実行でも利用上限に達した）。完了済みの担当に差分修正を頼むときは、長い作業履歴を持つ担当を何体も再開せず（再開すると履歴全体を読み直すため利用量が一気に増え、2026-10-06 に利用上限で全員が止まった）、修正項目をまとめて新しい担当1〜2体に依頼する。
- 依頼文で指定された slug・主検索語・切り口を守る。調べた結果、既存記事と同じ疑問に答える／一次資料で根拠を示せないと分かった場合は、書かずに理由を報告する（無理に書かない）。

## データ編集・検証・引き継ぎ

- 新規記事は `hp/content/blog/<slug>.json` に追加する（[形式](article-format.md)）。`articles.ts` 内の初期記事を直す場合だけ同ファイルを編集する。既存のカテゴリ・URL・公開日（`date`）を維持し、`updatedAt` は実質的な内容変更時だけ更新する。
- 新しい記事を追加したら、関連する既存記事（`articles.ts` の初期記事を含む）に新記事へのリンクを足す（品質チェック5）。
- 企画メモの「検証」欄は、最後に `check:articles`・lint・表示確認を実行した**後**に結果を書き込む（完了報告と同じ内容でよい）。
- 検証の順序: `npm run check:articles`（記事データの自動検証）→ `npm run lint` → 開発サーバー（`npm run dev`）で `/blog/<slug>` と `/blog` の表示をPC・スマホ幅で確認 → 必要なら `npm run build`（メモリ上限の拡張が必要な場合がある）。
- 自動検証の成功は事実の正確性や検索順位の改善を保証しない。出典の対応と読者の疑問への回答は別にレビューする。文字数は参考値として報告する。
- 完了報告は「対象記事と判断理由／根拠・未解決事項／変更ファイル／実施した検証／残る作業」を簡潔に示す。実行していない検証を成功扱いしない。
- ローカルでの編集・検証までは依頼範囲で進めてよい。**hp の main への push は本番（Vercel）に自動反映されるため、コミット・push・公開は社長の許可なしに行わない**（CLAUDE.md の Tier 2）。

## autosales で作った下書きとの関係

autosales（`/seo`）の「記事を生成」は、AI APIで下書きを作るだけで、検索結果の確認や一次資料の確認はしていない。下書きの中で根拠が必要な箇所には `【要出典】` が付く。`check:articles` は `【要出典】` が残る記事をエラーにするため、`seo-writer` が本ガイドに沿って調査・加筆・出典登録をしてから公開する。

基準の背景: Google の [people-first content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)。検索流入を目標にしても、固定文字数への水増しや未確認情報の量産をしない。
